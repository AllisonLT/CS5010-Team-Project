# REST API Contracts, Version 1 (Issue #16)

## Issue and milestone context

- **Issue:** #16 — Specify Java and Python REST API contracts
- **Milestone:** M2: Architecture, contracts, and development setup
- **Depends on:** #13 (`docs/shelf_life_feasibility.md`), #15 (`docs/data_model.md`)
- **Builds on:** the forecasting API already on the `Leyang` branch (`docs/fastapi.md`, `services/ml/src/cold_storage_ml/app.py`, `inference.py`)

There are two APIs:

```text
JavaFX desktop ──(A) Backend API──> Spring Boot ──(B) ML API──> FastAPI
                 127.0.0.1:8080                   127.0.0.1:8000
```

The desktop calls only API A. Only the backend calls API B.

## 1. Shared conventions

| Topic | Rule |
|---|---|
| Versioning | Every path starts with `/api/v1`. Adding optional request fields or new response fields is allowed within v1. Removing or renaming a field, changing its type or unit, or making an optional field required needs `/api/v2`. Clients ignore response fields they do not know. |
| Field naming | API A uses camelCase (Java convention). API B uses snake_case (already used by FastAPI). The backend maps between them. |
| Media type | `application/json; charset=utf-8`, except dataset upload (`multipart/form-data`) |
| Temperature | Always degrees Celsius. Field names end in `C` (API A) or `_c` (API B). The #11 dataset is confirmed to be Celsius (`docs/shelf_life_feasibility.md`). |
| Reading timestamps | Naive local ISO-8601, whole minutes where stated: `"2024-09-09T14:00:00"`. No `Z`, no offset. They come from the dataset, which has no time zone. |
| System timestamps | UTC ISO-8601 with `Z`: `"2026-11-07T20:01:09.412Z"` (`createdAt`, audit `timestamp`) |
| IDs | UUID strings generated by the backend |
| Supported horizons | 15, 30, and 60 minutes (the trained forecasting artifacts) |
| Supported product category | `FRESH_POULTRY_AEROBIC` only (#13) |
| Lists | Paged: `?page=0&size=50` (max 200). Response: `{ "items": [...], "page": 0, "size": 50, "totalItems": 312 }` |

### Error format (API A)

All errors from the backend use one shape, based on RFC 9457 problem details:

```json
{
  "status": 422,
  "code": "CSV_INVALID",
  "title": "The CSV file could not be used",
  "detail": "Missing required column 'Temperature'.",
  "errors": [
    { "field": "file", "row": null, "message": "Missing required column 'Temperature'" }
  ],
  "auditId": "9e1f4b7a-2c3d-4e5f-8a9b-0c1d2e3f4a5b"
}
```

`detail` is written for the user and shown as-is in the JavaFX error dialog. `auditId` points to the audit record of the failed operation, if one was written.

| HTTP | `code` | When |
|---|---|---|
| 400 | `MALFORMED_REQUEST` | Body is not valid JSON or a parameter has the wrong type |
| 404 | `DATASET_NOT_FOUND`, `PRODUCT_NOT_FOUND`, `PREDICTION_NOT_FOUND` | Unknown or deleted ID |
| 405 | `METHOD_NOT_ALLOWED` | Includes any attempt to change or delete audit records |
| 409 | `VERSION_CONFLICT` | Product was changed by another edit (optimistic lock) |
| 409 | `DATASET_NOT_READY` | Dataset is `MISSING_FILE` or `DELETED` |
| 413 | `FILE_TOO_LARGE` | Upload over 50 MB |
| 415 | `UNSUPPORTED_MEDIA_TYPE` | Upload is not a `.csv` file |
| 422 | `VALIDATION_FAILED` | A field is outside its allowed range (see `errors`) |
| 422 | `CSV_INVALID` | The file fails CSV validation (#21) |
| 422 | `INSUFFICIENT_HISTORY` | Fewer than 61 consecutive minutes before the forecast origin, or a gap over 10 minutes in a shelf-life window |
| 422 | `UNSUPPORTED_SENSOR` | The forecasting model was not trained for this sensor |
| 422 | `UNSUPPORTED_CATEGORY` | Product category other than `FRESH_POULTRY_AEROBIC` |
| 422 | `PRODUCT_NOT_LINKED` | Shelf-life request for a product without a temperature history |
| 500 | `AUDIT_WRITE_FAILED` | The operation could not be audited, so it was not completed (#19) |
| 500 | `INTERNAL_ERROR` | Anything else |
| 502 | `ML_BAD_RESPONSE` | ML service returned something that does not match API B |
| 503 | `ML_UNAVAILABLE` | ML service not running or not ready (models missing) |
| 503 | `DATABASE_UNAVAILABLE` | MongoDB not reachable |
| 504 | `ML_TIMEOUT` | ML service did not answer within 4 seconds |

The backend never returns a made-up prediction when the ML service fails, and never saves a failed prediction as a result.

Base URL: `http://127.0.0.1:8080` (`server.port`, env `BACKEND_PORT`).

### `GET /api/v1/status`

Always returns 200, so the UI can show which part is down.

```json
{
  "backend": "UP",
  "database": "UP",
  "mlService": "NOT_READY",
  "mlDetail": "Forecast artifacts are not ready",
  "checkedAt": "2026-11-07T20:00:00Z"
}
```

`database` and `mlService` are `UP`, `DOWN` (no connection), or `NOT_READY` (ML running but `/api/v1/ready` returned 503).

### `GET /api/v1/capabilities`

```json
{
  "forecastHorizonsMinutes": [15, 30, 60],
  "forecastMinimumHistoryMinutes": 61,
  "forecastSensorIds": ["SENSOR01", "SENSOR02", "SENSOR04"],
```

`forecastSensorIds` comes from the ML service (see section 3, change request 2). Until that exists, the backend reads it from configuration.

### `POST /api/v1/datasets`

`multipart/form-data` parts:

| Part | Required | Notes |
|---|---|---|
| `file` | yes | `.csv`, at most 50 MB |
| `displayName` | no | Defaults to the filename without extension. 1–100 characters. |
| `sensorId` | no | Required for `SENSOR_SEMICOLON` files when the filename has no `SENSORnn` pattern |

**201 Created**, `Location: /api/v1/datasets/{id}`. The body is the dataset detail described next.

**422 example** (row-level problems are listed, at most 20):

```json
{
  "status": 422,
  "code": "CSV_INVALID",
  "title": "The CSV file could not be used",
  "detail": "3 rows have an invalid date. Expected dd.mm.yyyy.",
  "errors": [
    { "field": "Date", "row": 2, "message": "'2024-09-02' is not dd.mm.yyyy" },
    { "field": "Date", "row": 3, "message": "'2024-09-02' is not dd.mm.yyyy" },
    { "field": "Date", "row": 4, "message": "'2024-09-02' is not dd.mm.yyyy" }
  ],
  "auditId": "1a2b3c4d-0000-4000-8000-000000000001"
}
```

### `GET /api/v1/datasets/{id}/readings`

Query: `sensorId` (required), `start`, `end` (naive local, optional; default is the whole range), `maxPoints` (default 2000, max 20000).

If the window has more minutes than `maxPoints`, the backend averages consecutive minutes into equal buckets and sets `downsampled: true`. Missing minutes are `null` and the chart shows them as gaps.

```json
{
  "datasetId": "6f0c1d1e-8a54-4f3e-9b35-0e2a4f6f1c11",
  "sensorId": "SENSOR02",
  "intervalMinutes": 1,
  "downsampled": false,
  "readings": [
    { "timestamp": "2024-09-09T13:00:00", "temperatureC": 7.4, "humidity": 71.0 },
    { "timestamp": "2024-09-09T13:01:00", "temperatureC": null, "humidity": null }
  ]
}
```

### `DELETE /api/v1/datasets/{id}`

**204 No Content.** See the deletion steps in #15.

### Products

`POST /api/v1/products` body (`PUT` takes the same body plus `version`):

```json
{
  "name": "Chicken breast batch 14",
  "category": "FRESH_POULTRY_AEROBIC",
  "initialLogCount": 2.0,
  "physiologicalStateAlpha0": 1.0,
  "temperatureSource": {
    "datasetId": "6f0c1d1e-8a54-4f3e-9b35-0e2a4f6f1c11",
    "sensorId": "SENSOR02",
    "start": "2024-09-08T18:05:00",
    "end": "2024-09-10T02:45:00"
  },
  "notes": "Received 2024-09-08"
}
```

| Field | Rule |
|---|---|
| `name` | 1–100 characters, required |
| `category` | Must be listed in `/capabilities` |
| `initialLogCount`, `physiologicalStateAlpha0` | Optional; ranges and defaults from `/capabilities` |
| `temperatureSource` | Optional. If given, the dataset must be `READY`, the sensor must belong to it, `start < end`, and both must be whole minutes inside the dataset's time range. |
| `notes` | 0–500 characters |
| `version` | Required on `PUT`; a stale value returns 409 `VERSION_CONFLICT` |

Responses add `id`, `status`, `version`, `createdAt`, `updatedAt`. `POST` returns 201, `PUT` returns 200, and `DELETE` returns 204.

### `POST /api/v1/predictions/temperature`

```json
{
  "datasetId": "6f0c1d1e-8a54-4f3e-9b35-0e2a4f6f1c11",
  "sensorId": "SENSOR02",
  "originTimestamp": "2024-09-09T14:00:00",
  "horizonsMinutes": [15, 30, 60],
  "thresholdC": 10.0
}
```

| Field | Rule |
|---|---|
| `originTimestamp` | Optional whole minute. Default: the latest minute that has 61 consecutive readings ending at it. |
| `horizonsMinutes` | Non-empty, unique, each 15, 30, or 60 |
| `thresholdC` | Finite, −50 to 60 |

The backend reads the 61 minutes ending at the origin from `minute.csv`, calls `POST /api/v1/predictions/temperature` on the ML service, saves the result, writes audit records (#19), and returns **201 Created**:

```json
{
  "id": "c3a2e9f1-1d7b-4a0e-8f4c-6b2d9e0a7f55",
  "type": "TEMPERATURE_FORECAST",
  "createdAt": "2026-11-07T20:01:09.412Z",
  "datasetId": "6f0c1d1e-8a54-4f3e-9b35-0e2a4f6f1c11",
  "sensorId": "SENSOR02",
  "originTimestamp": "2024-09-09T14:00:00",
  "currentTemperatureC": 8.1,
  "thresholdC": 10.0,
  "currentlyAboveThreshold": false,
  "forecasts": [
    { "horizonMinutes": 15, "targetTimestamp": "2024-09-09T14:15:00", "predictedTemperatureC": 8.4, "predictedPeakTemperatureC": 9.1, "predictedThresholdCrossing": false },
    { "horizonMinutes": 30, "targetTimestamp": "2024-09-09T14:30:00", "predictedTemperatureC": 8.9, "predictedPeakTemperatureC": 10.3, "predictedThresholdCrossing": true },
    { "horizonMinutes": 60, "targetTimestamp": "2024-09-09T15:00:00", "predictedTemperatureC": 9.6, "predictedPeakTemperatureC": 11.2, "predictedThresholdCrossing": true }
  ],
  "predictedMinTemperatureC": 8.4,
  "predictedMaxTemperatureC": 9.6,
  "warning": {
    "level": "WARNING",
    "message": "The temperature may reach 10.0 °C within 30 minutes."
  },
  "observedAfterOrigin": [
    { "timestamp": "2024-09-09T14:15:00", "temperatureC": 8.6 },
    { "timestamp": "2024-09-09T14:30:00", "temperatureC": 10.4 },
    { "timestamp": "2024-09-09T15:00:00", "temperatureC": 9.2 }
  ],
  "limitations": [
    "Minimum and maximum summarize the requested point forecasts only, not the full period.",
    "The peak estimate is an upper quantile, not a guarantee or a probability."
  ],
  "model": { "name": "damped_trend+future_peak_quantile_0.9", "version": "forecasting-2026-11-07", "mlServiceVersion": "0.1.0" },
  "durationMs": 412
}
```

All numbers in this example are illustrative.

| Field | Notes |
|---|---|
| `warning.level` | `CURRENT_VIOLATION` (reading already ≥ threshold), `IMMINENT` (crossing at 15 min), `WARNING` (at 30 min, not 15), `ADVISORY` (at 60 only), `NONE`. Same order as the ML alert policy, but computed per request by the backend. |
| `observedAfterOrigin` | Actual readings at each target time, taken from the dataset when they exist; `null` otherwise. The chart overlays them so the user can compare forecast and reality. These values are never sent to the ML service. |
| `limitations` | Shown under the results in the UI |

The UI uses `predictedMinTemperatureC` and `predictedMaxTemperatureC` for the PDF's "summary of predicted minimum and maximum temperatures," with the first limitation text next to them.

### `GET /api/v1/audit-logs`

Query: `eventType` (repeatable), `outcome`, `from`, `to` (UTC), `page`, `size`. Newest first. Fields are defined in #19.

`PUT`, `PATCH`, and `DELETE` on `/api/v1/audit-logs` and `/api/v1/audit-logs/{id}` return **405** `METHOD_NOT_ALLOWED`, and the attempt is itself audited.

## 3. API B: Backend → ML service

Base URL: `http://127.0.0.1:8000` (`app.ml.base-url`, env `ML_BASE_URL`). Timeouts: connect 1 s, response 4 s. The backend does not retry prediction calls automatically.

### Existing endpoints (from the `Leyang` branch)

| Method | Path | Used by backend | Notes |
|---|---|---|---|
| GET | `/api/v1/health` | Yes, for `/status` | Process is up |
| GET | `/api/v1/ready` | Yes, for `/status` | 503 if model artifacts are missing |
| POST | `/api/v1/predictions/temperature` | Yes | Contract below |
| POST | `/api/v1/alerts/current` | No | The backend checks the current reading against the threshold itself |
| POST | `/api/v1/alerts/evaluate` | **No** | Keeps alert state in Python memory, which is lost on restart. The backend owns persisted alert state and audit records. |

### `POST /api/v1/predictions/temperature`

This is the existing contract in `docs/fastapi.md`. Restated here for reference:

```json
{
  "sensor_id": "SENSOR02",
  "threshold": 10.0,
  "horizons_minutes": [15, 30, 60],
  "history": [
    { "timestamp": "2024-09-09T13:00:00", "temperature": 7.4, "humidity": 71.0 }
  ]
}
```

- `history`: 61 to 10,080 readings. The last 61 must be consecutive whole minutes. All values must be finite. Humidity must be 0–100. The backend sends exactly the 61 minutes ending at the origin.
- `sensor_id` must be one of the sensors the artifacts were trained on. Others return 422.
- Response fields used by the backend: `origin_timestamp`, `current_temperature`, `currently_above_threshold`, `predictions[].horizon_minutes`, `target_timestamp`, `predicted_temperature`, `predicted_peak_temperature`, `predicted_threshold_crossing`, `predicted_min_temperature`, `predicted_max_temperature`.
- Errors: 422 (invalid input or unsupported sensor), 503 (artifacts missing). FastAPI returns `{"detail": ...}`. The backend maps 422 to `INSUFFICIENT_HISTORY` or `UNSUPPORTED_SENSOR` when it can tell from the message, and to `VALIDATION_FAILED` otherwise. It maps 503 to `ML_UNAVAILABLE`.

### Change requests for the forecasting API

These are small, additive changes, allowed within v1. Owner: ML (Leyang).

1. **Unit:** change `"unit": "source_csv_unit_unconfirmed"` to `"unit": "celsius"`. The source is now confirmed to be Celsius.
2. **Supported sensors:** add `"sensor_ids": [...]` to the `GET /api/v1/ready` response, so the backend and UI know which sensors can be forecast.
3. **Model version:** add `"model_version"` to the prediction response (for example, the artifact folder name or a training date), so saved predictions record which model produced them.

### New: `POST /api/v1/predictions/shelf-life`

Implements #13 Option A. Owner: ML.

**Request:**

```json
{
  "category": "FRESH_POULTRY_AEROBIC",
  "initial_log_count": 2.0,
  "physiological_state_alpha0": 1.0,
  "future_temperature_c": 4.0,
  "interval_minutes": 1,
  "history": [
    { "timestamp": "2024-09-08T18:05:00", "temperature_c": 6.2 },
    { "timestamp": "2024-09-08T18:06:00", "temperature_c": null }
  ]
}
```

| Field | Rule |
|---|---|
| `category` | `FRESH_POULTRY_AEROBIC`; anything else returns 422 |
| `initial_log_count` | 1.0–4.0 |
| `physiological_state_alpha0` | 0.1–1.0 |
| `future_temperature_c` | Optional, 0–30; default is the last non-null reading |
| `interval_minutes` | Must be 1 in v1 |
| `history` | 60 to 20,160 entries (14 days). Consecutive whole minutes, strictly increasing. `temperature_c` may be `null` for missing minutes. The first and last entries must not be `null`. |

The service bridges runs of up to 10 `null` minutes by linear interpolation. A longer run returns 422 with the gap's start and end.

**Response (200):**

```json
{
  "category": "FRESH_POULTRY_AEROBIC",
  "history_start": "2024-09-08T18:05:00",
  "history_end": "2024-09-10T02:45:00",
  "future_temperature_c": 4.0,
  "remaining_shelf_life_hours": 64.3,
  "shelf_life_used_fraction": 0.72,
  "spoilage_risk": "medium",
  "estimated_log_count": 5.6,
  "past_spoilage_level": false,
  "factors": {
    "minutes_above_4c": 1730,
    "peak_temperature_c": 21.9,
    "mean_temperature_c": 9.8,
    "growth_share_above_4c": 0.91
  },
  "interpolated_minutes": 3,
  "flags": [],
  "limitations": [
    "Modeled estimate for fresh poultry in aerobic storage. Not a food safety determination.",
    "Based on air temperature in the storage room, not product temperature."
  ],
  "model": {
    "name": "pseudomonads_square_root",
    "version": "tsaloumi2022-v1",
    "citation_doi": "10.1016/j.psj.2022.101985",
    "parameters": { "b": 0.022, "tmin_c": -6.18, "spoilage_log_count": 7.0 }
  },
  "unit": "celsius"
}
```

Definitions of each output are in #13. `spoilage_risk` is `low`, `medium`, or `high`; the backend maps it to upper case.

**Errors:** 422 with `{"detail": "..."}` for invalid input, unsupported category, or a gap over 10 minutes. This endpoint needs no trained artifacts, so it works even when the forecasting models are missing.

**Example check (for #36):** a 1,440-minute history at a constant 4.0 °C with N0 = 2.0, α0 = 1.0, and `future_temperature_c` = 4.0 should give `shelf_life_used_fraction` ≈ 24 / 229.5 ≈ 0.105 and `remaining_shelf_life_hours` ≈ 229.5 − 24 = 205.5. Here 229.5 h (9.56 d) is the total shelf life at 4 °C with b = 0.022.
