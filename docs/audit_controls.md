# Audit Controls: AU-2, AU-3, AU-9, AU-12 (Issue #19)

## Issue and milestone context

- **Issue:** #19 — Map audit controls to application events and permissions
- **Milestone:** M2: Architecture, contracts, and development setup
- **Depends on:** #15 (`docs/data_model.md`), #16 (`docs/api_contracts.md`)
- **Implemented by:** #24 (audit writer, dataset events), #40 (audit review and restrictions), #41 (prediction and warning events), #44 (verification)

The project PDF requires audit logs that are generated automatically, stored separately in MongoDB, protected from modification through normal application use, and aligned with NIST SP 800-53 AU-2, AU-3, AU-9, and AU-12. This document maps each control to concrete behavior.

Scope boundary: this is a single-user local application. We implement the selected controls as described here. We do **not** add hash chains, digital signatures, or any certification claim; those are outside the PDF's scope.

## Control mapping

| Control | NIST intent (summary) | What the application does |
|---|---|---|
| **AU-2** Event Logging | Decide which events must be logged | The event catalog below is the complete list. Every state change and every failure in it is logged. |
| **AU-3** Content of Audit Records | Each record says what happened, when, where, the source, the outcome, and who was involved | Every record has the required fields listed under "Record format" |
| **AU-9** Protection of Audit Information | Protect audit records from unauthorized change and deletion | Separate `audit_logs` collection; the application's database account can only insert and read it; the API has no update or delete operation |
| **AU-12** Audit Record Generation | Records are generated by the system for the events in AU-2 | The backend service layer writes records automatically. The user cannot turn logging off or choose what is logged. |

## AU-2: Event catalog

| Event type | When | Outcome |
|---|---|---|
| `APPLICATION_STARTED` | Backend finishes startup | SUCCESS |
| `APPLICATION_STOPPING` | Backend receives a normal shutdown | SUCCESS |
| `DATASET_UPLOADED` | Upload accepted and stored | SUCCESS |
| `DATASET_UPLOAD_REJECTED` | File too large, wrong type, or fails CSV validation | FAILURE |
| `DATASET_UPLOAD_FAILED` | Valid file, but storage or database write failed | FAILURE |
| `DATASET_DELETED` | User deletes a dataset | SUCCESS / FAILURE |
| `DATASET_FILE_MISSING` | Startup check finds a `READY` dataset whose file is gone | FAILURE |
| `PRODUCT_CREATED` | Product created | SUCCESS / FAILURE |
| `PRODUCT_UPDATED` | Product changed, including linking a temperature history | SUCCESS / FAILURE |
| `PRODUCT_DELETED` | Product soft-deleted | SUCCESS / FAILURE |
| `PREDICTION_CREATED` | Temperature forecast or shelf-life estimate saved | SUCCESS |
| `PREDICTION_FAILED` | Prediction could not be produced (bad input, ML unavailable, timeout, bad ML response) | FAILURE |
| `THRESHOLD_WARNING_RAISED` | A temperature forecast returns a warning level other than `NONE` | SUCCESS |
| `SPOILAGE_RISK_HIGH` | A shelf-life estimate returns `HIGH` risk or is past the spoilage level | SUCCESS |
| `AUDIT_MODIFICATION_REJECTED` | A request tries to change or delete audit records through the API (405) | FAILURE |
| `SYSTEM_ERROR` | Any unhandled exception in a request | FAILURE |

Reading data, listing datasets, and viewing the audit table are **not** logged. They change nothing, and logging every view would bury the important events.

## AU-3: Record format

Collection `audit_logs` (shape agreed in #15):

```json
{
  "_id": "9e1f4b7a-2c3d-4e5f-8a9b-0c1d2e3f4a5b",
  "schemaVersion": 1,
  "timestamp": { "$date": "2026-11-07T20:01:09.412Z" },
  "eventType": "PREDICTION_FAILED",
  "source": "backend.PredictionService",
  "host": "laptop-bosun",
  "actor": "local-user:sunbo",
  "outcome": "FAILURE",
  "refs": {
    "datasetId": "6f0c1d1e-8a54-4f3e-9b35-0e2a4f6f1c11",
    "productId": null,
    "predictionId": null
  },
  "details": {
    "predictionType": "TEMPERATURE_FORECAST",
    "sensorId": "SENSOR02",
    "horizonsMinutes": [15, 30, 60],
    "thresholdC": 10.0
  },
  "error": {
    "code": "ML_UNAVAILABLE",
    "message": "ML service did not respond at http://127.0.0.1:8000"
  }
}
```

| AU-3 element | Field | Rule |
|---|---|---|
| What happened | `eventType` | One of the catalog values above |
| When | `timestamp` | Backend clock, UTC, millisecond precision, set when the record is written |
| Where | `source`, `host` | Component name (`backend.<ClassName>`) and machine host name |
| Source of the event | `source` | As above |
| Outcome | `outcome` | `SUCCESS` or `FAILURE` |
| Identity | `actor` | `local-user:<OS user name>`. The application has no accounts (out of scope), so this is the operating system user running the backend. |
| Objects involved | `refs` | IDs of the dataset, product, and prediction, `null` when not applicable |
| Further detail | `details`, `error` | Event-specific values. `error` is required when `outcome` is `FAILURE`. |

**What must not go into records:** full CSV contents, full reading histories, file system paths outside the upload directory, or stack traces. `details` stays under 4 KB; longer values are cut and marked `"truncated": true`.

## AU-12: How records are generated

- An `AuditService` in the backend is the only code that writes `audit_logs`. Service methods (upload, product changes, predictions) call it directly. A global exception handler calls it for `SYSTEM_ERROR`.
- No setting or API turns logging off or filters events.
- **Order of writes for successful changes:** do the change, then write the audit record, then report success. MongoDB runs as a single server in this project, so there are no multi-document transactions. If the audit write fails, the backend undoes the change (deletes the new document or file) and returns 500 `AUDIT_WRITE_FAILED`. A change is never reported as successful without its audit record.
- **For failures:** the backend tries to write the `FAILURE` record and then returns the original error. If the audit write also fails, it writes the event to the backend log file at `ERROR` level and returns the original error with `auditId: null`.
- Records are written once and never changed.

## AU-9: Protection

### In the application

- `GET /api/v1/audit-logs` is the only audit endpoint. `PUT`, `PATCH`, and `DELETE` return 405 and create an `AUDIT_MODIFICATION_REJECTED` record.
- The backend's audit repository exposes only `insert` and `find` methods. It does not extend Spring Data's `CrudRepository`, which would bring `save` (update) and `delete`.
- The JavaFX audit table is read-only: no edit, delete, or clear buttons.

### In MongoDB

The backend connects with an account whose roles allow only insert and read on `audit_logs`:

```javascript
// Run once by the setup script with an administrator account (#40).
db.getSiblingDB("cold_storage").createRole({
  role: "auditAppendOnly",
  privileges: [
    { resource: { db: "cold_storage", collection: "audit_logs" },
      actions: ["find", "insert", "createIndex"] }
  ],
  roles: []
});
db.getSiblingDB("cold_storage").createRole({
  role: "appData",
  privileges: [
    { resource: { db: "cold_storage", collection: "datasets" },
      actions: ["find", "insert", "update", "remove", "createIndex"] },
    { resource: { db: "cold_storage", collection: "products" },
      actions: ["find", "insert", "update", "remove", "createIndex"] },
    { resource: { db: "cold_storage", collection: "predictions" },
      actions: ["find", "insert", "remove", "createIndex"] }
  ],
  roles: []
});
db.getSiblingDB("cold_storage").createUser({
  user: "cold_storage_app",
  pwd: passwordPrompt(),
  roles: ["auditAppendOnly", "appData"]
});
```

- The built-in `readWrite` role is **not** used, because it would allow updating and deleting audit records.
- `remove` on `datasets`, `products`, and `predictions` is used only to undo a new document whose audit record could not be written (AU-12 above). User-facing deletes are soft deletes (`status: "DELETED"`).
- `predictions` gets no `update`, because predictions are never edited.
- The administrator account is used only by the setup script. Its password is not stored in the repository or in `application.properties`; the backend reads its own credentials from the `MONGODB_URI` environment variable.

**Change to local development setup:** the MongoDB container in `compose.yaml` currently runs without authentication (`docs/development.md`). That is fine for early development, but #40 must add an authenticated mode with the users above, and the demo and #44 verification must use it. Without authentication, the database permissions in this section do not apply.

### Verification (for #44)

| Check | Expected result |
|---|---|
| Call `PUT` and `DELETE` on `/api/v1/audit-logs/{id}` | 405, plus an `AUDIT_MODIFICATION_REJECTED` record |
| As `cold_storage_app`, run `db.audit_logs.updateOne(...)` and `deleteOne(...)` | MongoDB returns an "not authorized" error |
| Perform each catalog action once | Exactly one matching record, with every AU-3 field filled in |
| Stop MongoDB, then upload a dataset | Upload fails with an error, and no dataset becomes selectable |

## Limitations

- An administrator of the MongoDB server, or anyone with access to its data files, can still change records. Protection is against normal application use and the application's own account, as the PDF requires.
- The `actor` identifies the OS user, not a person, because the application has no login.
- Timestamps come from the local machine's clock and are only as accurate as that clock.
